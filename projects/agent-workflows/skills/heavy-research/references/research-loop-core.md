# Research Loop Core — 6步骨架 + 3通用强化

所有 subagent 都加载此文件。执行调研时严格按此流程。

## 6步骨架

每个 subagent 针对自己的维度，围绕 main agent 分发的**调研提纲**（子问题清单）执行。必须保留每个子问题的编号和 P0/P1/P2 优先级，不得在分解时丢失。

```
1. 分解   → 把提纲中属于本维度的子问题用 Depth×Breadth 树形展开（见下方强化 2）
2. 检索   → 对每个叶节点子问题执行检索（见各维度专项文件）
3. 提取   → 从结果中提取事实，写入 scratchpad（标注子问题编号 + 来源）
4. 差距   → 对比子问题树，标记哪些节点已 covered / 哪些仍有缺口
5. 循环   → 有缺口则生成 follow-up 继续（见强化 3），直到触发终止条件
6. 输出   → 将完整结果写入父 agent 指定的文件，对话只返回完成信号
```

---

## 强化 1：Reasoning Trace（每次检索前必做）

每次发出检索动作前，先在 scratchpad 写一段 reasoning trace，包含：
1. 当前子问题的真实意图（消歧，避免字面匹配）
2. 前几轮已确认的发现（缩小搜索空间）
3. 基于已知知识的假设性候选答案

检索时把 trace + query 一起作为检索上下文，而不是只用 query。

---

## 强化 2：Depth × Breadth 树形分解

把子问题清单做成树形，而不是平铺列表：

- **Breadth**：每层最多展开 N 个子话题（建议 3-5）
- **Depth**：最多递归 2 层（叶节点才真正执行检索）
- 每深入一层，breadth 自动减 2（浅层广泛，深层聚焦）
- 判断一个子问题是否可继续拆分：能拆出 2 个以上独立子话题则拆，否则直接检索
- 去重：若新子问题与已检索话题语义等价，跳过

---

## 强化 3：差距驱动 Follow-up

每轮检索后评估结果质量：
- 信息充足（覆盖子问题的核心事实）→ 标记该节点为 `covered`
- 信息不足（模糊、矛盾、缺关键细节）→ 生成针对缺口的 follow-up query，继续检索

不是机械跑固定轮次，而是"查到够了才停"。

---

## 终止条件（双判据，任一触发即停）

1. **质量判据**：子问题树所有 P0/P1 叶节点均标记为 `covered`；P2 叶节点允许在预算不足时列入“未执行”
2. **预算判据**：tool call 次数达到上限（联网 subagent 上限 30 次，源码 subagent 上限 20 次，记忆 subagent 上限 10 次）

预算不足时的执行顺序：
1. 先覆盖 P0 叶节点
2. 再覆盖 P1 叶节点
3. 最后覆盖 P2 叶节点
4. 如果预算触顶，已经尝试但仍无充分结果的节点写入“已尝试但未覆盖”；因预算不足根本没执行的节点写入“未执行”；两者都不得隐式当作 covered

---

## 输出格式

调研完成后，将完整结果**写入文件**（具体路径由父 agent 在 prompt 中指定；联网写 `<SESSION_DIR>/research/web.md`，源码写 `<SESSION_DIR>/research/source.md`，记忆写 `<SESSION_DIR>/research/memory.md`）。

文件结构：下方“有...时写 / 无...时只写”是写作分支说明，最终报告每个小节只能选择一个分支，不得原样保留这些说明行。

```markdown
# <维度> 调研报告 — YYYY-MM-DD-HHmmss

## 子问题 #1（P0）：<提纲中的原文>
### 结论与证据
- 有结论时写：
  - <结论>
  - 来源：<URL / 文件路径 / brv 节点>
  - 置信度：confirmed
  - 推理：<1-2 句说明依据>
- 无结论时只写：
  - 无

### 已尝试但未覆盖
- 有尝试但未覆盖时写：
  - 尝试：<查询或路径>
  - 原因：<无结果 / 结果矛盾 / 超出范围>
- 无此类内容时只写：
  - 无

### 未执行
- 有未执行项时写：
  - 项：<子问题或路径>
  - 原因：<预算不足 / 不属于本维度 / 前置条件缺失>
- 无未执行项时只写：
  - 无

## 子问题 #2（P1）：...

## 元数据
- run_id: <父 prompt 提供的本轮 run_id>
- tool call 总次数：N
- 树形覆盖率：X/Y 叶节点
- 调研轨迹摘要：<3-5 行 reasoning trace 摘要>
```

标题中的 `P0`、`P1` 和置信度里的 `confirmed` 都只是示例值。每个子问题标题必须带优先级，且优先级必须与父 prompt 的调研提纲一致，只能写 `P0`、`P1`、`P2` 三者之一；每条结论的置信度只能写 `confirmed`、`unverified`、`CONFLICT` 三者之一。不得保留 `P0/P1/P2`、`confirmed / unverified / CONFLICT` 这类斜杠枚举占位，也不得写没有优先级的 `## 子问题 #N：...` 标题。

**关键约束**：
- 写入父 prompt 指定的 research 报告文件是本 subagent 唯一允许的写操作；不得修改源码、PWF、ByteRover 或其他项目文件
- 元数据必须写入父 prompt 提供的 `run_id`；没有 run_id 的报告会被父 agent 视为旧轮残留
- 每个子问题必须保留 `### 结论与证据`、`### 已尝试但未覆盖`、`### 未执行` 三个小节；没有对应内容时只写 `- 无`，不得保留来源 / 置信度 / 原因等模板占位，也不得保留“有...时写 / 无...时只写”说明行。空小节里的 `- 无` 不算 covered
- 子问题标题优先级、结论置信度和 `run_id` 都是父 agent 机械校验字段；字段缺失、非法或保留斜杠枚举占位会导致该维度重跑
- 写完文件后，整个对话回复**只能是一行**父 prompt 指定的精确完成信号：`Done: web` / `Done: source` / `Done: memory`
- 不许在对话里返回摘要、解释或任何其他文字
- 理由：父 agent 通过文件读取详细内容，对话回复仅作完成信号，避免 transcript 占用父 context
